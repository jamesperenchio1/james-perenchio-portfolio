# Build Prompt — James Perenchio Personal Portfolio

You are building a personal portfolio website for **James Perenchio**, a systems &
infrastructure professional moving into information security. Build the whole thing,
make it production-quality, and deploy it. Read this entire brief before starting.

The single most important architectural requirement: **the site must be content-driven
and easy to scale.** Building the site and adding a project are two different jobs. After
you build the system, James must be able to add or expand a project by editing/adding
**one content file** — never by touching component code. Nothing about individual projects
should be hard-coded into components.

---

## 1. Stack

- **Next.js (App Router, latest 14.x) + React, deployed on Vercel.** Vercel runs Next.js
  natively so the assistant API route works with zero config.
- **Content in MDX.** Use `next-mdx-remote` (RSC/server-component variant) + `gray-matter`
  to read MDX files from a `/content` directory. Each project is one `.mdx` file with
  YAML frontmatter (structured fields) + an MDX body (freeform, can embed custom React
  components — video, callouts, interactive demos). If you prefer an equivalent robust
  MDX-as-data setup, that's fine; the requirement is **project = one content file**, and
  the body must support rich embeds so some projects can be far more elaborate than others.
- **`next-themes`** for a light/dark toggle.
- **`framer-motion`** for motion (see Design → Motion).
- Keep dependencies lean; don't pull in a heavy CMS or component kit. Plain CSS/CSS-modules
  or Tailwind — your call — but keep it clean and maintainable.

---

## 2. Architecture & the "add a project" workflow

Suggested layout (adapt names sensibly, keep the spirit):

```
/content/projects/<slug>.mdx      ← ONE file per project (frontmatter + MDX body)
/content/site.(ts|json)           ← global config: name, tagline, socials, certs, about copy
/app/page.js                      ← home: hero, about, project gallery, certs, contact
/app/projects/[slug]/page.js      ← reads the MDX, applies that project's theme
/app/api/assistant/route.js       ← Gemini endpoint (server-side key)
/components/mdx/*                  ← custom MDX components (VideoEmbed, Callout, Highlights, Diagram, Figure, etc.)
/components/*                      ← Nav, ThemeToggle, ProjectCard, Assistant, Contact, Certs, Footer
/public/James_Perenchio_CV.pdf    ← résumé (James will drop this in; wire the download to it)
```

- The home gallery is generated by **reading all project frontmatter** and sorting by an
  `order` (or `date`) field. Adding an `.mdx` file automatically adds a themed card + a
  full themed page. No component edits.
- The project page reads that file's frontmatter `theme` block and paints itself (see §4).
- Put **"How to add a new project"** instructions in the README: copy an existing
  `.mdx`, change the frontmatter, write the body. That's the whole workflow.

**Frontmatter schema** (every project file):


## 3. Global design direction

Tone: **nice, inviting, cool, innovative — NOT edgy.** Confident but warm. Feature-rich
but light to use. Think "sharp indie engineer portfolio," not "corporate template" and not
"hacker-edgelord."

- **Base theme is LIGHT**, with a **dark/light toggle in the top-right** of the nav
  (persist choice). The light base is the default surface for home, gallery, certs, contact.
- **Per-project pages override the palette** with their own theme (§4) regardless of the
  global light/dark setting — each project is its own mood. Transition the palette smoothly
  when navigating into a project.
- **Typography:** pick a tasteful pairing yourself (no strong preference from James). A
  characterful display face + a clean body face + a mono for labels/eyebrows works well.
  Load via `next/font` (Google fonts fine).
- **Motion: make it feel alive** — James explicitly wants lively motion, not a stripped-back
  reduced-motion experience. Use framer-motion for: page/route transitions, staggered
  reveal-on-scroll for sections and cards, expressive hover states on project cards
  (lift/tilt/glow using the card's accent), and an animated theme/palette transition on the
  project pages. Keep it smooth and performant (GPU-friendly transforms, no jank). Still
  honor `prefers-reduced-motion` as a graceful fallback, but the **default** experience is
  animated and rich.
- **Layout:** generous whitespace, a comfortable max content width (~1040px), strong
  hierarchy. Fully responsive; mobile-first solid.
- Accessibility: semantic HTML, keyboard-navigable, sufficient contrast in **both** themes
  and on every project palette, alt text, focus states.

## 4. Per-project theming system

Each project's `theme` frontmatter defines CSS custom properties applied to a wrapper on
that project's page (and used to tint its gallery card — e.g. a top accent bar / hover glow).
Implement it generically: read the `theme` object → set `--bg/--surface/--border/--text/
--muted/--accent/--accentText/--display/--mono` → all project-page styling references those
vars. This is what makes each project "its own world" without bespoke code per project.

Seed theme tokens for the six projects are embedded in §6. New projects just supply their own.

### Project 1 — Lekha  *(featured; order: 1)*
- kind: "AI · Application Security"
- tagline: "An AI assistant that lives inside LINE — and a case study in securing an autonomous agent."
- stack: TypeScript, Next.js, Vercel AI SDK, Gemini, Upstash Redis / QStash
- links: live https://lekha-iota.vercel.app · code https://github.com/assistantforyou/lekha
- theme: bg #0a0b12 · surface #14121f · border #2a2350 · text #EAE8FF · muted #9d97c9 · accent #7c6bff · accentText #0a0620 · display Space Grotesk · mono IBM Plex Mono  *(dark, electric violet — flashy/alive)*
- **intro:** A personal assistant you add on LINE like a friend. It remembers things, sets
  reminders, reads photos and voice memos, manages your Google Calendar and Drive, and sends
  email from your own Gmail — all in plain language.
- **body:**
  - Lekha runs entirely inside LINE and is public by design: every user gets isolated memory,
    connects their own Google account, and is rate-limited individually. The genuinely hard
    part isn't the chat — it's making an autonomous LLM agent safe to expose to the open internet.
  - That constraint drove the whole architecture. An agent that can send email and touch your
    calendar is only as trustworthy as the controls around it, so the interesting work was in
    identity, integrity, and least privilege.
- **highlights** (render as a styled list — this is the security-engineering core):
  - **Trust at the edge:** Every inbound webhook (LINE, QStash) has its HMAC-SHA256 signature
    verified against the raw body with a timing-safe comparison before any work runs. Forged
    requests never get in.
  - **Identity it can't be talked out of:** The user's identity is bound from the verified
    webhook, never from model output — so the agent can't be socially-engineered into acting
    as someone else.
  - **Secrets at rest:** Google refresh tokens are encrypted with AES-256-GCM. The OAuth flow
    is hardened against CSRF and replay with signed, single-use links and short-lived
    server-side nonces.
  - **Guardrails on action:** Anything with real consequences is drafted, queued, and gated
    behind an explicit YES (shown verbatim), plus per-user rate limiting and webhook replay
    de-duplication.
