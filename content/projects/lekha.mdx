## Overview

Lekha is a personal AI assistant you add on LINE like any other contact. You talk to it in
plain language and it remembers things about you, keeps task lists, sets one-off and
recurring reminders, searches the web, reads photos, receipts, and voice memos, manages your
Google Calendar and Drive, and sends email from your own Gmail, attachments included. There's
no app to install. Everything happens in a chat thread people in Thailand already use every
day.

Anyone can find it on LINE, but using it is gated. New users get a free trial with a daily
limit, and after that they need a paid plan, a promo code, or my approval. Every user who gets
through connects their own Google account, so Lekha ends up holding real credentials for real
people and can take real actions with them. Most of the engineering time went into making
that safe.

## The problem

Once a language model can send email and edit a calendar, the controls around it matter more
than the model. I designed around three risks:

- A forged request that pretends to come from LINE or from my own job queue.
- The model being talked into acting as a different user, or into using someone else's
  Google account.
- A misread instruction turning into an email that can't be unsent.

The approach throughout was to establish identity cryptographically, keep the model inside
that identity, and give it as little room as possible to do irreversible things on its own.

## Security architecture

**Webhook integrity.**
Every request from LINE carries an `X-Line-Signature` header. Lekha computes HMAC-SHA256 over
the exact raw body and compares it in constant time before doing anything else, so the check
can't be probed with timing and a tampered request is dropped before it reaches application
code. Callbacks from the QStash job queue are verified the same way using Upstash's signature.
Each event is also de-duplicated by its webhook event ID for ten minutes, so a replayed or
retried request doesn't run twice.

**Identity comes from the webhook, not the model.**
The user ID is taken from the verified webhook and bound to the request before the model is
involved. Tools that send or read anything use that bound ID to look up tokens. They never
accept a user ID as an argument from the model. A prompt injection can change what the model
says, but it can't change whose account it's operating on.

**Refresh tokens encrypted at rest.**
Connecting Google means storing a long-lived refresh token, which is about the most sensitive
thing the system holds. Those tokens are encrypted with AES-256-GCM using a dedicated 32-byte
key, so a copy of the database alone doesn't give anyone access to users' Google accounts.

**A hardened OAuth flow.**
The link that starts a Google connection is an HMAC-signed token, and the flow uses a
server-side nonce stored in Redis with a ten-minute lifetime that can only be used once. An
intercepted or reused link is useless, and you can only finish a connection you started
yourself.

**Confirmation gate on anything visible to other people.**
Sending an email or creating a calendar event never happens straight from a model turn. The
model can only call draft tools, which push the action onto a per-user pending queue that
expires after five minutes. Lekha then shows the exact draft (recipients, subject, body,
attachments, times) and waits. A YES in English or Thai runs the queued actions. NO, or
anything else, clears the queue.

**Access control and abuse limits.**
Every message passes an access gate first: admins, allowlisted users, and active trial users
get through, and everyone else gets a sign-up card. There's also a per-user sliding-window
rate limit, so a stuck retry loop or someone hammering the bot can't burn through the model
quota or trigger a flood of actions.

**Isolation between users.**
Memory, task lists, reminders, connected Google accounts, and rate limits are all scoped per
user. One person's data and permissions never show up in another person's session.

## How it's built

Lekha is a TypeScript app on Next.js, deployed on Vercel. The LINE webhook verifies the
signature, returns 200 right away so LINE doesn't retry, and processes the event in the
background. The Vercel AI SDK and Mastra handle the model (Gemini) and tool calls, Upstash
Redis holds per-user state and memory, and QStash runs scheduled work like reminders and
scheduled emails outside the request path. The tool layer wraps Gmail, Google Calendar,
Drive, and Contacts. Photos, voice memos, and files forwarded in LINE are handled inline, so
you can send a picture of a receipt and ask it to log it, or forward a PDF and ask it to email
it to someone.
